# 阶段 01 实施记录：服务器环境与许可证

**状态：已完成；执行日期：2026-10-31（北京时间）。** 最终验收运行 `20261031_02`。公开证据内机器时间保留原始工具输出和 UTC 字段，不作为性能对照实验的时间数据。

## 做了什么

1. 使用本机既有专用 SSH 密钥登录学校服务器，执行 `whoami`、`hostname`、`pwd` 与内核/资源查询；身份和主机与既有连接配置一致。公开仓库不记录账号、地址、私钥或实际私有主目录。
2. 确认本项目服务器根目录原先不存在，以 `umask 077` 新建 `$HOME/opentitan_aon_timer_4525bin_repro` 及 `project/`、`src/`、`runs/`、`scratch/01/`、`evidence/01_env/`、`runtime/`。既有项目未被改写。
3. 现场核对 RHEL 7.9、glibc 2.17、GCC 4.8.5、系统 Python 3.6.8，找到 VCS/URG P-2019.06-SP1 和其附带 UVM 1.2；`verisim`/`vericov` 未在当前 PATH 中发现，本次使用 VCS/URG 路线。
4. 新写 UVM 探针，编译、运行、导出真实 functional group coverage。完整采样命中 4/4；少采样对照命中 3/4。两份报告各仅含 1 个测试，不把合并结果当单次向量。
5. 在新目录独立安装 Python 3.11.7 并创建 `.venv`。17 个分析/配置处理依赖离线安装并锁定，基础运算、DBSCAN、解析器及 `pip check` 通过。
6. 导出 25 个脱敏证据文件，记录原始服务端文件和输入源码 SHA-256；服务器及本机独立复核均通过。

## 为什么这么做

本阶段验证商业工具的实际编译、运行、覆盖采样和报告能力，而不只检查命令是否存在。4-bin 小探针及 3/4 负对照能够发现覆盖未写出、混合报告和筛选错误；它们不是 AON Timer 覆盖模型，永不参与正式复现统计。

Python 运行时与分析库独立安装，避免依赖旧实验的可变环境。只复用了已缓存、且与发布者索引 SHA-256 一致的通用 Miniconda 安装包，未导入任何旧 379-bin 数据、仿真产物、manifest 或聚类结果。

### 2. Python 独立安装和离线依赖

安装包：`Miniconda3-py311_24.1.2-0-Linux-x86_64.sh`。

- 发布者索引：`https://repo.anaconda.com/miniconda/`，本次独立查询确认 SHA-256。
- SHA-256：`3f2e5498e550a6437f15d9cc8020d52742d0ba70976ee8fce4f0daefa3992d2e`。
- 从既有本地缓存读取安装包，校验后复制到新 `$ROOT/runtime/`，再次校验后安装；没有复用旧 Python 环境。

服务器首次安装实际命令：

```bash
cd "$ROOT/runtime"
printf '%s  %s\n' 3f2e5498e550a6437f15d9cc8020d52742d0ba70976ee8fce4f0daefa3992d2e Miniconda3-py311_24.1.2-0-Linux-x86_64.sh | sha256sum -c -
env -u LD_PRELOAD -u LD_LIBRARY_PATH timeout --signal=TERM --kill-after=10s 300s bash Miniconda3-py311_24.1.2-0-Linux-x86_64.sh -b -p "$ROOT/runtime/miniconda3"
"$ROOT/runtime/miniconda3/bin/python" -m venv "$ROOT/.venv"
```

服务器在线 pip 安装因 DNS 失败退出 1，随后在本机针对 CPython 3.11 / manylinux2014 下载二进制 wheels：

```powershell
python -m pip download --index-url https://pypi.org/simple --only-binary=:all: --platform manylinux2014_x86_64 --python-version 311 --implementation cp --abi cp311 --timeout 20 --retries 1 --disable-pip-version-check --dest ".stage_review/wheels" -r "01_服务器环境与许可证/requirements-stage01.txt"
```

下载到 17 个 wheels，使用 Python `hashlib.sha256` 逐一生成 `SHA256SUMS`，以 `tarfile` 打包并通过 SCP 上传。原始 `stage01-wheels.tar` SHA-256 为 `08147d33898d1f753fe958a523d77f3ee3e6140c0b99b6f12ec75dbc7348399f`，服务器解包前再次核对。每个 wheel 的哈希见 [wheel_sha256sums.txt](evidence/public_20261031_02/wheel_sha256sums.txt)。重新下载时使用完整锁文件 `requirements-stage01.lock.txt`，避免传递依赖漂移。

本目录脚本经 SCP 上传到 `$ROOT/project/stage01/` 后，实际执行：

```bash
bash "$ROOT/project/stage01/bootstrap_python.sh"
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 \
  "$ROOT/.venv/bin/python" "$ROOT/project/stage01/inspect_environment.py"
"$ROOT/.venv/bin/python" -m pip check > "$ROOT/evidence/01_env/pip_check.txt"
"$ROOT/.venv/bin/python" -m pip freeze > "$ROOT/evidence/01_env/pip_freeze.txt"
```

`bootstrap_python.sh` 已实际执行成功；本次它复核前述新安装的运行时，并完成离线依赖安装。它不会覆盖已存在的 Python 安装；发现不完整的同名目录会停止。系统 Python、学校许可配置和启动文件均未修改。

## 失败处理

1. **继承的 LD_PRELOAD 指向缺失库**：版本查询出现两条 OpenSSL 共享库加载警告。对本阶段工具子进程使用 `env -u LD_PRELOAD`；Python 安装时另移除 `LD_LIBRARY_PATH`，未更改用户启动文件，也未清除许可证变量。
2. **首次 URG 报告失败**：裸测试名 `full_seed42` 不被 URG 2019 接受。保留初次日志和原脚本，改从工具实际输出解析完整逻辑测试名，在新 `20261031_02` 目录全部重跑。[失败返回码](evidence/public_20261031_02/first_attempt_return_codes.tsv)、[错误日志](evidence/public_20261031_02/first_attempt_urg_full.log)。
3. **服务器包索引 DNS 失败**：在线 pip 返回 1；使用本机下载的哈希校验 wheels 离线安装。[在线失败日志](evidence/public_20261031_02/pip_online_failure.log)。
4. **Windows 哈希清单 CRLF**：首次 `sha256sum -c` 将行尾 CR 作为文件名的一部分。修正脚本为 `tr -d '\r' < SHA256SUMS | sha256sum -c -` 后 17 个 wheels 全部通过；没有变更 wheel 字节或放宽哈希检查。
